# Coding Workflow

Approved plans enter the `approved-coding` pg-boss queue. [Repository Setup](repository-setup.md) supplies editable, saved runtime profiles; `internal-chat-ui`, `elation_companion`, and `workplace-agents` also have built-in defaults. Other repositories can run through a configured profile. A repository with no saved profile or built-in default produces a visible preparation failure rather than silently leaving an approved plan idle.

## Lifecycle

Each run is bound to the approved plan version, plan hash, requirements hash and source commit. Each step has a separate ID, job, input commit, result and logs. The stages are workspace preparation, Codex implementation, saving the code checkpoint, collecting evidence, repository validation, Claude adversarial review, preserving the review result/evidence, and controller-owned GitHub publication. Findings of critical, high or medium severity return to implementation; a material decision pauses for Tim. There is no review-round budget or provider fallback.

The ticket page shows these steps, summaries, findings, validation results and log links. Failed steps have a Retry action and a deliberate Use Branch and Retry form when a fresh branch is needed. A publication already in flight must be reconciled before its branch can change. A changed ticket, removed Plan label, changed repository selection or revised plan prevents obsolete attempts from advancing. A revised approved plan starts a separate run; previously used branches are not silently reused.

### Repeated Validation Failures

A first failed validation returns to implementation. If a completed implementation attempt leaves the candidate commits unchanged and validation again returns the same command/exit-code results, the controller pauses in **Your Direction Needed** instead of repeating. It preserves both validation results, identifies the previous step, and uses the existing **Reply and Continue** flow. This compares command outcomes, not individual test identities or log text; inspect the logs to diagnose the actual failure.

The comparison uses the latest completed validation for the same repository, coding run, change request and human reply. Changed candidate commits, different command outcomes or a new reply allow another attempt. Passing validation follows the normal next-repository/review path. The pause never marks failed validation as passed or authorizes publication.

Verification on October 22, 2026: `make verify` passed (70 tests, lint/format, types and build), and `make test-intake` passed eight PostgreSQL integration tests; the opt-in OrbStack setup test was skipped. Regression coverage exercises an actual failed-validation/implementation/failed-validation cycle, no queued continuation after the pause, preserved work, stale-result rejection, reply/restart/resumption, and the normal passing path for single and multiple repositories. These are local fixtures; check live ticket history for deployment and incident recovery evidence.

Optional optimizations and controls: Tim approved this stopping condition on October 22, 2026 after ONE-5005 completed 58 failed validations of the same commit. It applies to all coding runs; an unchanged repeated command failure now requires human direction even if its underlying cause is transient. There is no added round cap, retry, test suppression or validation waiver.

Linear's `updatedAt` timestamp alone does not change discovery inputs. PR integrations can update that timestamp without changing the ticket's content. Intake compares saved ticket content and repository selections, including for runs created before this correction; existing approval hashes remain unchanged.

## Execution and Evidence

Each ticket run uses one isolated OrbStack workspace with a private container engine and repository-owned local services. Candidate checkouts live together at `/work/<repository>`, allowing paired acceptance tests. Repository commands run through `/work/run.mjs --repo <repository>`, which loads only the repository's mapped and attempt-owned environment. The source is restored from the approved commit into an independent Git repository. Synced clones are read-only inputs. Provider credentials arrive through stdin, not command arguments or the controller's environment. GitHub and notification credentials are not copied into the guest.

New steps ensure the guest runtime matches the deployed worker release, including its frozen SDK dependencies. Running steps keep their existing runtime.

Both SDKs use Agent Models settings at the start of each step. Global, coding and repository-specific prompt settings apply to implementation and review. The guest has its own official Playwright MCP server, browser profile and Chromium installation. Its localhost points to its own app. The repository's locked Playwright browser is installed separately for its tests.

SDK events, tool results and validation output enter central Logs under service `coding`, ticket and step ID. A redacted mirror lives in `/work/logs/structured/coding.jsonl`, with full payloads in `/work/logs/artifacts`, allowing agents to inspect their own failures without credentials to other tickets' logs. Application/test screenshots and other evidence live under `/work/evidence`. The host retains evidence archives in `data/coding/<run>/<step>-evidence.tar.gz`. Logs and saved step results are redacted using the provider key and the attempt environment before persistence.

Codex implements repositories sequentially in confirmed repository order. The controller saves each checkpoint in its own bare repository, validates it, then advances to the next repository. ICU runs `pnpm lint/check/test/build`; Companion runs its existing `bash ./build.sh`; Workplace Agents runs root `make validate`. Agents must also execute the approved plan’s acceptance tests. Intermediate repositories can defer paired browser acceptance until the final candidate exists; the final implementation must supply real browser evidence.

Claude then reviews the complete candidate set, including cross-repository behavior. Unresolved critical/high/medium findings restart a sequential revision pass; all candidate commits must have passing validation and the combined review before publication. No repository is published after only its individual validation. Checkpoint sets are captured on each step, so changing either candidate invalidates publication evidence. Source changes in other checkouts during implementation, or any checkout during review/validation, fail the step.

Multi-repository checkpoints and publication intents live under `data/coding/<run>/<repository>/`; legacy single-repository paths remain readable. PR publication proceeds one repository per durable job. Each successful PR URL is persisted before advancing, and retries reconcile the current repository’s saved intent instead of republishing the previous repository. The detail page shows ordered repository progress and every PR.

## Recovery and Publication

Guest agents and validation run in named systemd units with process-group ownership. Cancellation stops the owned unit, including SDK, shell and browser descendants. Completed agent results are atomically saved in the guest before transport and on the host before the database transition. Checkpoint saving and evidence collection are separate jobs, carrying the saved result and original agent attempt ID. Checkpoints use stable Git refs in the guest and host, so interruption after a commit or export does not create another commit on replay. Retry preserves the existing working tree; it never hard-resets uncheckpointed implementation work. Failed/preparing workspaces are retained for diagnosis, with their IDs in the workspace manifests. They are not automatically deleted. Tim approved a 60-minute hard deadline per coding step on October 20 after ONE-5190 exceeded the inherited 15-minute default while still making progress. Every newly queued step, including retries, explicitly receives 3,600 seconds. Each repository implementation, validation, review and publication step has its own deadline. An expired worker reports the duration and preserves completed checkpoints. Agent execution, validation and publication do not gain automatic retries. Existing jobs retain the expiration recorded when they were queued.

Checkpoint and collection jobs use native pg-boss retries: two retries, ten seconds apart, then a visible failure. They repeat only preservation work, never an agent call. Startup reconciliation recovers completed agent receipts and resumes interrupted preservation jobs; exhausted attempts remain paused. Job retry counts fence stale workers from advancing a newer attempt. A completed result awaiting a database transition is recovered from its receipt rather than rerunning the SDK.

Evidence collection freezes the finished agent's evidence and log mirror once in `/work/receipts/<agent-step>/`, outside both source trees. Archives are written to a temporary host file, checked for readability, and atomically renamed. Retry reuses the frozen snapshot. Browser evidence can be a file or a nonempty directory, with canonical paths constrained to the saved evidence tree. The additional frozen copy stays with the workspace for diagnosis. Command failures retain executable, arguments, exit code and full redacted stderr in Logs.

The UI identifies checkpoint saving and evidence collection separately. After an evidence failure, **Retry Evidence Collection** resumes from the saved candidate. Existing pre-upgrade failures lack durable receipts; recovering their already-completed agent output requires an explicit audited import of the original result. The additive database migration preserves old steps. Do not roll back to a worker that does not understand `checkpoint`/`collect` while those stages are pending.

Optional optimizations and controls introduced by this recovery change: Tim requested bounded retries for safe preservation stages. Two retries with a ten-second delay apply only to checkpoint/evidence jobs, delaying a persistent failure by approximately twenty seconds while preserving code and avoiding repeated agent execution. No global retry policy was changed.

Recovery verification (October 21, 2026): PostgreSQL integration tests cover a dead worker, process restart, two native retries followed by exhaustion, manual collection retry with unchanged inputs, and rejection of stale completion/failure writes. Filesystem tests cover interrupted receipt/snapshot writes, immutable replay, directory evidence and path escapes, plus complete redacted command diagnostics. A disposable Git fixture in Mia's OrbStack guest was interrupted immediately after its commit; recovery exported the same commit and subsequent replay created no additional commit. These tests do not simulate disk loss or a full Mac power failure.

Publication runs from Mia's login-session worker, where the operator's GitHub keychain identity is available. SSH sessions cannot necessarily access that keychain. The controller requires passing validation and code review for the exact commit, inspects all existing PR states and the remote branch, checks compatibility with the current default branch, and records publication intent before writing. A new branch is pushed with an expected-absent ref lease. On an uncertain retry, an existing branch/PR must match the saved intent and exact commit. Unexpected changes, closed/merged branches and merge conflicts require attention. Agents never merge, enable auto-merge or deploy the managed application.

## GitHub PR and Main Workflow Tracking

The existing `github-pr-refresh` pg-boss queue checks published, unfinished coding runs every five minutes, independently of Linear intake. The worker uses Mia’s login-session GitHub CLI credentials. Home’s **Refresh GitHub** queues a check of unfinished runs; the ticket's **Check GitHub** action checks a specific run, including completed work. Use **Refresh View** in the coding actions dropdown to reload the observed result.

Each repository retains its own PR, merge commit, workflow runs and observation timestamp. A multi-repository ticket reaches Done only when every repository satisfies the completion rule. A merge saves the PR’s merge commit and time. **Done** requires the PR to have merged into `main`, at least one matching workflow, and success for every observed GitHub Actions run with `event=push`, `head_branch=main`, and that exact merge SHA. This is repository-independent: PR checks, manual workflows, unrelated commits, and separate production promotions cannot satisfy the rule. No matching run means **Waiting for Main Workflow**; pending runs mean **Main Workflows Running**. Non-success terminal conclusions, including cancelled or skipped workflows, mean **Main Workflow Failed**. Done and active states are green; failures and closed-unmerged PRs are yellow. The detail page links each workflow and shows its attempt and outcome.

All pages of matching workflow runs are read through the GitHub REST API. The workflow’s reported conclusion is the completion evidence; Code Assist does not independently verify application health or require a repository-specific deployment job. A later matching run cannot be anticipated: Done reflects all runs observed at that check. Completed runs can be explicitly refreshed. Previous merge-only Done records are reopened for a workflow check on upgrade.

GitHub read failures preserve the previous state and show an error. If workflow metadata is available but failure logs are unavailable, the failure remains visible and repair waits for diagnostic evidence. Scheduled/manual refresh reads again. Observations are ordered by check start time so delayed responses cannot overwrite newer evidence. Events and central Logs (`service=github`) retain the transitions; failures, completion and closed-unmerged PRs use the existing Teams flow. Observation never changes Linear state or grants new plan approval.

On Home, tickets remain in the main list for 24 hours after their latest transition to Done. Older completed tickets appear in the collapsed **Completed** section at the bottom, with the same links and green badges. This uses the current coding run’s saved completion event, not the PR merge time or last GitHub check. Refreshing Home updates the grouping; reopened or corrective work returns to the main list.

## Corrective Coding After a Failed Main Workflow

For a still-current approved plan, a failed main workflow captures the complete failed-job logs and the attempt-specific job list in a redacted central artifact. A separate coding run retains the original plan approval, parent run, merge commit, workflow IDs and attempts. Repeated observations of that failure do not create duplicate coding jobs. A changed failure attempt or observed recovery supersedes unpublished stale repair work; existing published corrective PRs remain for Tim to review.

The new run provisions its own isolated OrbStack workspace from the failed merge commit, which already contains the feature. Git objects are fetched into the run’s private bare repository; synced clones and old workspaces are preserved. The controller verifies that this base remains in main’s history. Agents read full evidence at `/work/evidence/main-workflow-failure.json` and use the existing central logging and Playwright MCP integration. Codex diagnoses and repairs only defects within the approved feature/repository. Missing credentials, transient/environmental incidents, shared CI/IAM changes, or expanded scope require a concrete diagnosis and Tim’s direction.

A justified code fix follows the same implementation → lint/type checks/tests/build → Claude review loop. It opens a fresh `feature/<ticket>-main-fix-<run-id>` branch and corrective PR, preserving the merged PR and never reusing its branch. Tim merges; agents do not dispatch deployment workflows or deploy. The corrective PR must merge and its own main workflows must succeed before the current ticket shows Done. Old failures remain visible as history. Removed or superseded approvals still permit observation, but do not authorize automatic repair.

For multi-repository runs, repair targets one failed repository at a time while retaining the other candidate checkouts and their PR outcomes. Combined review still covers the pair. A new corrective PR replaces only the failed repository’s completion requirement; every other repository must also complete. Failed and active workspaces are retained; eligible completed guests use the [completed workspace cleanup](#completed-workspace-cleanup) workflow while host checkpoints and evidence remain. Automatic ingestion of GitHub review comments and automatic rebase/revalidation remain unimplemented. Requested Code Changes and Bring In Main below are explicit user actions.

## Requested Code Changes

For a ticket with current open PRs, **Request Code Changes** in the coding actions dropdown opens a **Request Changes** form for refinements to the implementation. Submission saves the request, owner, time, original PR URLs and published commits with the next pg-boss implementation step in one transaction. Duplicate or stale submissions cannot start a second revision. Earlier requests, plans, steps and evidence remain available.

Codex resumes the saved workspace and branch. The usual checkpoint, evidence collection, validation and Claude review loop runs again, sequentially across repositories where applicable. Every step carries the request ID: old validation and reviews cannot authorize a new revision even if its commit is unchanged. Material scope changes still require a revised approved plan. Closed or merged PRs cannot be revised through this action.

Before coding and publication, the controller checks that the PR is still open, belongs to this coding run, and has the recorded branch head. Publication requires the new commit to descend from that head, then pushes with an explicit expected-head lease. A per-request publication intent allows a retry to recognize a successful push whose response was lost. The existing PR URL is retained, its summary records the request and updated candidate commits, and no second PR is opened. GitHub polling cannot overwrite a running revision with a stale PR observation.

Verification covers two successive requests, duplicate submission, worker restart, revision retry, Claude-driven revision loops, fresh evidence binding, and single/multiple repositories using PostgreSQL fixtures. Local Git publication tests cover actual guarded pushes, lost-response recovery, changed remote heads, and closed/merged/unowned PR rejection; GitHub API responses are fixtures. No paid agent run or live feature-branch update is initiated by those tests.

Optional optimizations and controls: none. Request binding, PR ownership and expected-head checks preserve approval and publication integrity.

## Missing Browser Evidence

Missing browser evidence appears in an alert with a **Run Browser Checks** action. That action starts a fresh Codex attempt from the saved checkpoint; it does not replay the incomplete result. Even a no-code-change attempt must perform its browser checks. Evidence transfer failures with a valid browser receipt still retry collection without rerunning the agent.

## Replies to Coding Questions

When coding is paused in **Your Direction Needed**, **Your Reply** and **Reply and Continue** appear beneath the agent's question. Tim can answer, paste reference examples, clarify requirements, or withdraw an earlier request. The question, reply, actor and timestamp are saved transactionally with the next pg-boss step and remain in **Previous Replies**. This works before publication and during revisions to an open PR.

The agent continues from the existing workspace and checkpoints. Multiple repositories proceed sequentially again so each gets the clarified requirements. Both Codex and Claude receive the replies; explicitly accepted operational tradeoffs must not repeatedly block the same work. Publication requires fresh validation and review tied to the latest reply, even when the commits are unchanged. Existing plan approval, stale-submission, workspace and closed/merged PR checks remain in effect. Replies do not merge PRs or deploy code.

## Bring In Main

**Bring In Main**, a separate item in the coding actions dropdown, starts a normal code revision for open PRs. It can also resume a blocked code revision that already has an open PR. Existing checkpoints and feedback remain intact; a blocked revision retains its recorded published head separately from any newer unpublished checkpoint.

The controller fetches `main` into a request-specific Git ref in each host bare repository and supplies a bundle to the guest. No GitHub credentials enter the guest. Each repository's main commit is pinned when its implementation starts and reused on retry. Codex merges that local ref using `--no-commit --no-ff`, resolves conflicts while preserving upstream changes, and runs checks. The controller saves the merge commit, including both parents even when the merge has no tree changes. Unresolved conflicts are preserved and cannot be checkpointed as resolved code.

Validation and Claude review run again for the exact revision. Reviews compare the feature against the supplied main commit. Publication requires both the previous published head and the pinned main commit to be ancestors of the candidate, then updates the same PR with the existing expected-head check. This is an explicit action; subsequent changes to main do not trigger automatic synchronization. It does not rewrite branch history or merge the PR.

Verification includes real local Git merges/conflicts, interrupted bundle delivery, pinned-commit replay, merge ancestry, empty-tree merges, unchanged-main handling, and checkpoint replay. PostgreSQL fixtures exercise single/multiple repositories, duplicate submissions, blocked-revision resumption with unpublished work, and fresh validation/review binding.

Optional optimizations and controls: none. Pinning and ancestry checks preserve the requested merge and its reviewed history.

GitHub fields use [gh pr view](https://cli.github.com/manual/gh_pr_view), [workflow runs](https://docs.github.com/en/rest/actions/workflow-runs), and [workflow jobs](https://docs.github.com/en/rest/actions/workflow-jobs).

Optional optimizations and controls: the approved repeated-validation pause described above. Approval fencing, commit-bound validation/review, process ownership and expected-head publication are required workflow integrity checks.

## Completed Workspace Cleanup

The `completed-workspace-cleanup` pg-boss job checks every five minutes for coding runs that have remained **Done for more than 24 hours**, using the latest `coding_done` event (the same timestamp as the home page archive). It removes only that run's owned OrbStack VM. Work in progress, open PRs, failed/blocked/superseded runs, and visually paused work do not become eligible merely because they are old. Every repository must have successful main-workflow evidence.

Before deleting a VM, cleanup locks the ticket against coding/status transitions, checks for unfinished steps and dependent/shared runs, verifies final review/validation against the saved commits, reads the host Git objects and saved evidence archives, and checks that the VM has no active agent unit, unsaved checkout changes, or different HEAD. It saves a final archive of `/work/evidence`, `/work/logs`, available results/receipts, and repository `.tmp` artifacts, then verifies the archive and records its SHA-256 in `data/coding/<run-id>/workspace-cleanup.json`. Missing or inconsistent evidence blocks deletion; the ticket's Coding panel displays the reason and a later scheduled check can try again.

Cleanup retains the database history, plans, discovery snapshots, host bare Git repositories/checkpoints, original evidence archives, centralized logs/artifacts, final archive, and workspace metadata. Repair preparation can still read its parent's saved Git repository. The VM's installed dependencies, build outputs outside the evidence locations, runtime credentials and disposable local test databases are removed with the VM; this is not a full-machine backup. New validation code must put durable test evidence in `/work/evidence` or repository `.tmp`, not leave it only in a test database or arbitrary ignored directory.

The manifest is saved before deletion. If the worker exits after OrbStack deletes the VM but before the database records completion, the next check verifies the retained archive and finishes recording cleanup. Repeated jobs do not repeat completed cleanup or change Done. The Coding panel shows when resources were cleaned. Application release pruning and log retention are separate policies and are not changed here.

Optional optimizations and controls: Tim requested the 24-hour completed-work cleanup; it removes the local preview/test environment while keeping durable work records. Five-minute polling follows the existing lifecycle monitor cadence. No additional retention, release-pruning, or cache policy is introduced.

## Windmill Production Fork Publication

For `OnetoOneHealth/windmill-work`, Code Assist follows the production workspace workflow in `docs/dev-do-this-every-time.md`. Repository-specific instructions explain the difference from interactive development: agents implement and test locally; only the controller creates and publishes the fork, after the exact candidate passes validation and Claude review. The current integration targets `workspaces/production`. Changes to another workspace need its matching publication integration; they cannot be deployed through the production fork.

The controller uses the existing secret named `WINDMILL_WINDMILL_PRODUCTION_PERSON_TOKEN` (including a consolidated alias) from Code Assist's secret store. The publication credential is not added to repository mappings or passed to the agent guest. It verifies the configured account, the parent Git Sync connection, the fork's parent/ownership, and native deploy-on-push behavior. It does not edit Git Sync settings, create credentials or enable copied triggers.

A local branch such as `feature/one-5302` publishes as `wm-fork/main/one-5302` to workspace `wm-fork-one-5302`. The ordinary branch remains the local coding branch; other repositories in a combined run retain their own normal publication path. Fresh branches create fresh forks. Requested changes to an owned open PR reuse that run's fork. Closed/merged PRs, foreign forks and unexpected remote commits are not overwritten.

Native fork creation seeds its branch from main. Publication replaces only that recorded seed, with an explicit expected-head lease, with the exact validated/reviewed candidate. It does not silently merge newer main changes into the candidate. The existing merge-conflict check still runs. Native Git Sync applies the push to the fork; the controller waits for successful sync metadata naming that exact commit before recording success. Waiting observes Windmill's asynchronous jobs and respects the coding step's existing cancellation/expiry; it does not retry failed API requests or create new timeout/retry policies. Failed syncs surface their native job link. If Windmill opens the PR during synchronization, Code Assist attaches its validation evidence to that PR; otherwise the existing GitHub PR publisher creates it.

`data/coding/<run>[/<repository>]/windmill-fork.json` records fork creation, account, initial branch head and deployment evidence for recovery. An ambiguous branch-creation response stops for reconciliation rather than blindly creating another fork. The Coding card and PR include the fork and successful deployment-job links.

This proves eligible source content reached the fork. It does not prove live business behavior or provision resources, variables, schedules, triggers or datatable state excluded by native Git Sync. ONE-5302's datatable, webhook route and Elation subscription therefore remain separate plan/acceptance requirements. Human review and PR merge still control production publication.

Validation uses real local Git repositories with synthetic Windmill/GitHub responses, including exact-commit publication, native PR adoption, restart recovery, ownership collisions, failed sync and cancellation. Live read-only inspection confirmed the configured account, production connection, automatic fork sync and existing fork deployment metadata on Windmill EE v1.845.0. A new real fork publication remains to be exercised by the first approved, reviewed Windmill coding run.

Optional optimizations and controls: none. Fork ownership, exact-commit evidence and expected-head checks preserve the requested publication workflow.
